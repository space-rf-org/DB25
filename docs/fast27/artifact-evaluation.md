# Artifact Evaluation prep

Artifact Evaluation runs **after** acceptance (fall-cycle artifact deadline: Thu
Dec 17, 2026), so it consumes none of the current eight days. It's here because
DB25 is unusually well positioned to sweep it, and because the two or three
changes that make AE easy are worth making regardless of venue.

Verify specifics against the [FAST '27 Call for
Artifacts](https://www.usenix.org/conference/fast27/call-for-artifacts) — this
section follows USENIX's standing three-badge scheme.

---

## The badges

| Badge | Requirement | DB25 today |
|---|---|---|
| **Artifacts Available** | Publicly archived with a DOI at a permanent repository (Zenodo, figshare, Software Heritage). A GitHub URL alone does not qualify — GitHub is not permanent. | **Not done** — needs a Zenodo deposit. ~1 hour. |
| **Artifacts Functional** | Documented, consistent, complete, exercisable. Reviewers build it and run the tests. | **Nearly there.** `cmake && ctest` already works from a clean recursive clone. |
| **Results Reproduced** | An independent party reproduces the paper's main results. | **Blocked** — depends entirely on which results the paper claims. |

## Why DB25 is strong here

Most artifacts fail AE for boring reasons: they don't build on a clean machine,
the README skips a step, a dependency is unpinned, or the numbers in the paper
can't be regenerated by any script in the repo. DB25 already avoids most of that:

- One command builds everything from a recursive clone.
- `ctest --test-dir build --output-on-failure` runs the entire suite.
- The toolchain is pinned and stated (GCC 14+, C++23, `-fno-exceptions`).
- CI runs the full suite under ASan+UBSan, so "works on my machine" is already
  disproven.
- 47 committed golden fixtures make correctness claims mechanically checkable by
  a reviewer with no domain knowledge.
- The falsifiability gate lets a reviewer verify that the tests are *capable of
  failing* — a claim almost no artifact can support.

Foreground the gate in the artifact README. It is the most interesting thing in
the artifact and reviewers will not find it on their own.

## Gaps to close

1. **No DOI.** Deposit a tagged release to Zenodo (link the GitHub repo, cut a
   release, Zenodo mints a DOI). Do this for the umbrella repo with submodules
   vendored in, or the deposit will be an empty shell. **Required for
   "Available".**
2. **Submodules break archival.** A GitHub tarball of `DB25` does *not* include
   `external/` submodule contents. Produce a self-contained archive:
   ```sh
   git clone --recursive https://github.com/space-rf-org/db25 db25-artifact
   cd db25-artifact && rm -rf $(find . -name .git -maxdepth 3)
   cd .. && tar czf db25-fast27-artifact.tar.gz db25-artifact
   ```
   Verify by building from the extracted tarball on a machine with no network.
3. **No container.** A pinned Dockerfile removes the single largest source of AE
   friction — a reviewer on the wrong GCC. GCC 14 + CMake + Ninja, `ctest` as the
   default command. ~1 hour, high return.
4. **No results-reproduction script.** Whatever the paper's headline numbers are,
   ship one script that regenerates them and prints them in the paper's own units
   and table order. **Required for "Results Reproduced".** The most common AE
   failure is a reviewer who can run the tests but cannot find Table 3.
5. **No stated resource envelope.** Tell reviewers what the artifact needs: cores,
   RAM, disk, and wall-clock for both the smoke path and the full run. Provide a
   fast path (< 10 min) and a full path.
6. **Anonymization during review.** If AE is double-blind for your cycle, the
   artifact must be anonymized too — Zenodo deposits and Docker Hub images both
   carry identity. Check the CFA; use anonymous.4open.science if required.

## Artifact README skeleton

Keep it to one page above the fold. Reviewers are volunteers on a deadline.

```markdown
# Artifact: <paper title>

## Claims supported
- Claim 1 (paper §5.1, Table 2): ... → reproduced by `./scripts/repro_table2.sh`
- Claim 2 (paper §5.3, Figure 4): ... → reproduced by `./scripts/repro_fig4.sh`
Claims NOT supported by this artifact: <be explicit — reviewers reward candor>

## Requirements
Hardware: <cores, RAM, disk>.  OS: <...>.  Toolchain: GCC 14+, CMake ≥3.20, Ninja.
Full run: ~<N> minutes.   Smoke run: ~<M> minutes.

## Quick start (smoke, < 10 min)
    docker build -t db25-artifact . && docker run --rm db25-artifact

## From source
    cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=Release
    cmake --build build -j && ctest --test-dir build --output-on-failure

## Reproducing each result
<one subsection per table/figure: exact command, expected output, runtime,
 and the tolerance within which a reviewer's numbers should match yours>

## What makes this artifact checkable
The suite is falsifiability-gated: `db25_gate` requires that every injected
mutant is caught by at least one test, and reports any test that no mutant can
make fail as a defect. Run it to verify the tests can actually fail:
    ./build/db25_gate
```
